# AI231 Meta-Agent Factory — Architecture Contract v1.0

Status: **Architecture specification committed; WANGA runtime integration remains pending.**
This document defines the factory that creates digital agents. It does not define a recruitment or marketplace system.

## 1. Mission

Convert a project, repository, Wix site, research program, or bounded work request into one or more versioned, testable digital-agent blueprints. Materialize and execute only agents whose blueprints pass validation and explicit operator activation.

## 2. System boundary

The factory creates:
- Agent identity and mission
- System instructions and operating invariants
- Capabilities and least-privilege tool permissions
- Input and output contracts
- Handoff and dependency declarations
- Safety boundaries and failure behavior
- Acceptance tests and version metadata

The factory does **not** recruit people or third-party agents, grant credentials, publish websites, contact partners, spend money, deploy code, or perform destructive operations by default.

## 3. Pipeline

1. **Project intake** — collect source references, goal, constraints, and evidence.
2. **Project understanding** — inventory relevant Wix sites, GitHub repositories, documents, and existing runtime components; preserve source provenance.
3. **Gap analysis** — identify work units and missing capabilities without inventing facts.
4. **Agent architecture** — define the minimal specialist agents, their boundaries, and explicit handoffs.
5. **Blueprint compilation** — emit schema-valid versioned blueprints.
6. **Static verification** — validate required fields, permission allowlists, boundary coverage, dependencies, and acceptance-test presence.
7. **Human activation gate** — draft is the default; activation is an explicit operator action.
8. **Materialization** — generate a runnable package or adapter for an approved runtime.
9. **Runtime verification** — execute acceptance tests in an isolated environment and record evidence.
10. **Registry and lifecycle** — retain version, provenance, status, test evidence, and supersession links.

## 5. Blueprint lifecycle

`draft -> validated -> approved -> materialized -> tested -> active -> deprecated`

A failed validation or test moves the blueprint to `blocked`. A changed specification creates a new version; it does not silently overwrite a running version.

## 6. Permission model

Use an explicit allowlist. Unknown permissions fail closed. The first AppDeploy implementation allows only:
- `generate_text`
- `analyze_supplied_data`
- `read_public_web_content`
- `create_internal_task`
- `write_internal_report`
- `read_agent_registry`

External publishing, payments, messaging, outreach, account administration, arbitrary code deployment, destructive operations, and unrestricted network egress are excluded. Credentials are never generated by the model or embedded in a blueprint.

## 7. Source and evidence rules

- Preserve repository paths, commit references, file hashes, and Wix site identifiers as provenance where available.
- Distinguish **Verified**, **Assessment**, **Hypothesis**, and **Unresolved**.
- Do not infer implementation from a name, plan, README, or generated blueprint.
- Do not invent project constants, weights, gate semantics, or missing source definitions.
- Preserve AI231 invariant: **Logic Before Weights; WEIGHTS = NOT_CREATED**.

## 8. Validation requirements

Every blueprint must contain:
- Mission and system instructions
- At least two capabilities
- At least one permission from the allowlist
- At least two input requirements
- At least three explicit boundaries
- Output contract
- At least three acceptance tests
- Failure behavior
- Semantic version

Activation must fail if any required section is missing. Execution must fail for a draft, blocked, deprecated, or unapproved blueprint.

## 9. Runtime contract

The materializer must:
- Produce a reproducible package from a specific blueprint version.
- Execute in an isolated environment.
- Deny network egress by default.
- Expose only explicitly granted tools.
- Record inputs, tool calls, outputs, errors, and test results.
- Stop and return a structured failure when a task exceeds its permissions or acceptance criteria.

## 10. Current deployment boundary

The AppDeploy Agent Foundry now includes a Master Agent Builder UI and backend routes for creating, listing, validating/activating, and bounded execution of custom agent blueprints. AppDeploy QA reported zero frontend and backend errors for that deployment.

This does **not** prove that WANGA-X, LNL, the historical private-agent runtime, all Wix sites, or all GitHub repositories are already connected to the live app. Those integrations remain separate work items and must be verified individually.
